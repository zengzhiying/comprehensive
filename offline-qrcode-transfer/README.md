# 二维码单向传文件（内网 → 外网）

两个 Python 脚本，利用「内网机器的画面通过远程桌面显示在外网机器屏幕上」这一条现成的
视觉通道，把文件从内网搬到外网。全程没有任何网络连接、不需要摄像头、不需要 U 盘。

```
┌─────────────────── 内网（隔离网）───────────────────┐
│  sender_windows.py                                  │
│  把文件切片 → 每片一个二维码 → 在窗口里按节奏轮播    │
└─────────────────────────┬───────────────────────────┘
                          │  远程桌面（RDP / VDI 客户端）
                          │  画面显示在外网机器的屏幕上
┌─────────────────────────▼───────────────────────────┐
│  receiver_windows.py                                │
│  对屏幕的一块区域连续截屏 → 解码 → 按序号拼回文件     │
│  → 收齐后校验整文件 SHA-256 → 落盘                   │
└─────────────────────────────────────────────────────┘
```

数据只能单向流动：内网往外网发。外网没有任何回传通道，所有「重发」都由人手动操作。

---

## 一、安装

两台机器都需要 **Python 3.8 或更高**（Windows 官方安装包自带 tkinter，装的时候
记得勾选 `tcl/tk`，默认是勾上的）。

### 内网机器（发送端）

```
pip install qrcode
```

只依赖 `qrcode` 这一个纯 Python 包。二维码是用 tkinter 画布自己画的，**不需要装 Pillow**。
把 `sender_windows.py` 一个文件拷（或用剪贴板粘贴）过去就能跑。

### 外网机器（接收端）

```
pip install mss pillow opencv-python-headless pyzbar
```

| 包 | 作用 | 能不能省 |
|---|---|---|
| `mss` | 截屏（快，支持多显示器） | 可退化成 Pillow 的 ImageGrab，但装它最好 |
| `pillow` | 图像处理、界面预览 | 必需 |
| `pyzbar` | 二维码解码（**主力**） | **强烈建议装，见下方说明** |
| `opencv-python-headless` | 解码兜底 | 可省，但没了兜底 |

> **关于 pyzbar，实测结论：不要省。**
> 本地拿**没有任何压缩、没有任何畸变的干净图像**做版本扫描，两个解码器的结果：
>
> | 二维码版本 | 模块数 | pyzbar | OpenCV |
> |---|---|---|---|
> | v4 | 41 | ✅ | ✅ |
> | v10 | 65 | ✅ | ✅ |
> | v15 | 85 | ✅ | ❌ |
> | v21 | 109 | ✅ | ✅ |
> | v26 | 129 | ✅ | ✅ |
> | v31 | 149 | ✅ | ✅ |
> | v35 | 165 | ✅ | ❌ |
> | v40 | 185 | ✅ | ❌ |
>
> OpenCV 即使对完全干净的图像也会**随机失败**，而 pyzbar 在所有版本上 100% 成功。
> 所以 OpenCV 只当兜底，真正干活的是 pyzbar。没装 pyzbar 时接收端会在启动扫描时
> 用红字提醒你。Windows 上 `pip install pyzbar` 的 wheel 自带 zbar 动态库，不需要
> 额外装东西；Linux 上要 `apt install libzbar0`。

## 二、快速上手

### 1. 摆好屏幕

* 外网机器用远程桌面客户端连上内网机器，**建议全屏、用原生分辨率、显示比例 100%**。
  如果客户端做了缩放（「智能缩放」「适应窗口」），二维码会被插值糊掉，识别率会掉。
* 外网机器上再开 `receiver_windows.py`，**把它的窗口拖到不遮挡二维码的位置**
  （比如屏幕最右边）。接收端自己也会出现在截屏范围里，只要不压住二维码就没事。

### 2. 内网：发送

```
python sender_windows.py
```

1. 点【选择文件…】选要发的文件；
2. 确认【分包大小】等参数（默认 800 字节 / 0.4 秒，见第四节）；
3. 点【开始发送】。

界面会依次经历三个阶段，状态栏上都有提示：

| 阶段 | 画面 | 说明 |
|---|---|---|
| ① 起始帧 | 一个小二维码 | **停留 10 秒**，等接收端就位。里面有文件名、大小、分包大小、总包数、起始序号 |
| ② 数据帧 | 大二维码连续轮播 | 每 0.4 秒换一张，最后一张是最后一包 |
| ③ 结束帧 | 小二维码 | 一直显示，里面有整文件的 SHA-256。**别急着关**，等接收端报「校验通过」 |

### 3. 外网：接收

```
python receiver_windows.py
```

1. 设好【输出目录】（默认在桌面上的「二维码接收」文件夹）；
2. 截屏范围先保持「整个屏幕」，或者点【框选二维码区域】把内网窗口里二维码那块框起来
   （框小一点更快更稳，推荐）；
3. 点【开始扫描】；
4. 等。右边大字会显示「接收中…等第 N 包」，进度条会走。

> **框选的要点：按「数据帧」的大小来框，不要按起始帧。**
> 起始帧的二维码很小，数据帧的二维码大得多（默认参数下大约 700 像素见方）。
> 如果只框住起始帧那一小块，后面的大二维码会被裁掉边缘，接收端就会不停漏帧、不停报缺包。
> 稳妥的做法是：**先让发送端跑起来进到传输阶段，再对着那个最大的二维码框**，
> 框比二维码每边多留出二三十像素。
> 实在不确定就用「整个屏幕」，慢一点但不会错。

收齐后接收端会自动：

* 检查 0 ~ 总包数-1 是不是一个不缺；
* 算出收下来的文件的 SHA-256，和结束帧里带的比对；
* 两者都通过才把 `.qrtpart` 改名成正式文件放进输出目录，并大字显示「✔ 传输完成」。

**任何一步不过，都不会生成最终文件**，只会报错——不会出现「看起来成功了的残缺文件」。

### 4. 收完收工

接收端报「✔ 传输完成」后，两边的【关闭】按钮随便点，直接关窗口也行。

## 三、缺包了怎么办（重点）

这是唯一需要人工介入的地方。

**接收端的表现**：某个包没扫到（比如远程桌面卡了一下），接收端立刻变红报警：

```
⚠ 缺第 37 包！
已停止接收。
请把发送端【起始序号】
改成 37 后点【重发起始帧】
```

按最初的设计，从第 37 包往后的数据**一律不再接收**，就停在那儿死等第 37 包。

**你的操作**（在内网发送端窗口上）：

1. 点【暂停】（或者不暂停也行，反正接收端已经不收了）；
2. 把【起始序号】改成接收端报的那个数字（例子里是 `37`）；
3. 点【重发起始帧】。

发送端会重新播一次起始帧（10 秒），接收端一看起始帧的起始序号是 37、其它参数都对得上，
就知道这是续传，从第 37 包接着收。**前面 0~36 包的数据还在，不用重传。**

> 小提示：接收端报警时会响一声铃。如果两边是同一个人操作，看到红字照做即可。

### 如果不小心传完了但报「还缺 N 包」

说明发送端是从中间开始发的、而接收端前面根本没有那些包（比如接收端换了输出目录、
或者第一次就是从中间开始发的）。接收端会列出缺哪些（比如 `0~36、40`），
把【起始序号】改成缺的第一个包重发即可。

### 如果报「整文件校验失败」

说明收下来的字节和原文件对不上——可能是发送端的文件在中途被改过，或者硬盘层面的问题。
这种情况**不能续传**，接收端会把这次的数据判为不可信，需要：

1. 接收端点【放弃本次会话】（会删掉临时文件）；
2. 发送端把【起始序号】改回 0；
3. 重新完整传一遍。

## 四、参数怎么选

### 分包大小（字节）

一个分片打包成一个二维码。帧里除了数据还有约 42 字节的头部（版本号、会话号、序号、
校验码等），数据本身还要 base64（膨胀 1/3），所以：

**二维码实际字符数 ≈ 分包大小 × 1.34 + 42**

| 分包大小 | 帧字符数 | QR 版本 | 模块数 | 纠错级别 M 下的余量 |
|---|---|---|---|---|
| 400 B | ~570 | v19 | 101 | 很宽松 |
| 600 B | ~835 | v23 | 117 | 宽松 |
| **800 B（默认）** | ~1103 | v27 | 133 | 合适 |
| 1200 B | ~1635 | v34 | 161 | 偏紧 |
| 1600 B | ~2170 | v39 | 181 | 极限 |
| 1716 B | ~2340 | v40 | 185 | 纠错级别 M 的上限 |

纠错级别各档的单包上限（界面上会自动算好显示）：L ≈ 2184、M ≈ 1716、Q ≈ 1215、H ≈ 924 字节。

**建议**：先用默认 800 跑一次，如果接收端经常缺包，就降到 400~600 重试；
扫描很稳、想快一点，再往 1200 加。

### 帧间隔（秒）

每个二维码在屏幕上停留多久。太小了远程桌面来不及把画面刷过去，接收端会扫到撕裂的
中间态（解不出来，浪费一帧）；太大了纯粹是浪费时间。

`帧间隔 ≥ 2 ÷ 采样帧率` 才不会漏帧。采样帧率默认 8 帧/秒，所以间隔别低于 0.25 秒。
**默认 0.4 秒**是比较稳的选择。

### 纠错级别

二维码自带纠错，远程桌面的有损压缩会引入误码，级别越高越耐操，但能装的数据越少。

* **M（默认，约 15% 容错）**：推荐；
* Q（约 25%）：如果你那边远程桌面压缩特别狠（画面明显发糊），换 Q 并相应减小分包；
* L：只适合画面非常清晰、带宽很足的情况；
* H：一般用不上，装得太少。

### 采样帧率 / 同一帧确认次数（接收端）

* **采样帧率**：每秒截屏解码几次。默认 8 次/秒。屏幕小、框选区域小可以调到 15~20；
  CPU 吃紧或区域很大就降到 4~5。
* **同一帧确认次数**：同一个二维码要被独立解出几次才算数，默认 2 次。
  这是防误码的第二道保险（第一道是帧内的 CRC32）。嫌慢可以设 1，
  但**不建议**——设 1 时一次侥幸的误读就可能被当成真数据。

> 接收端还有个自动优化：如果这一帧画面和上一帧完全一样，就直接沿用上次的解码结果，
> 不重复解码。所以轮播停留期间 CPU 占用很低。

## 五、耗时估算

理想速度 = 分包大小 ÷ 帧间隔，再扣掉起始帧的 10 秒。**每次缺包后的人工续传还要额外
花 10 秒（起始帧停留）+ 你操作的时间**，所以实际耗时通常比表里多 10%~30%。

| 分包 | 间隔 | 速度 | 100 KB | 500 KB | 1 MB | 5 MB |
|---|---|---|---|---|---|---|
| 400 B | 0.4 s | 1.0 KB/s | 1.7 分 | 8.3 分 | 17 分 | 83 分 |
| **800 B** | **0.4 s** | **2.0 KB/s** | **0.9 分** | **4.2 分** | **8.5 分** | **43 分** |
| 800 B | 0.6 s | 1.3 KB/s | 1.3 分 | 6.4 分 | 13 分 | 64 分 |
| 1200 B | 0.4 s | 3.0 KB/s | 0.6 分 | 2.8 分 | 5.7 分 | 28 分 |

文件越大越要耐心。**几十 MB 以上不建议用这套工具**，几个小时的传输里几乎一定会遇到
需要人工续传的情况。

## 六、协议格式

所有帧都是纯 ASCII 文本，字段用 `|` 分隔，二进制内容一律 base64。
发送端和接收端各自文件里都有一份独立的协议定义，**改动时必须两边同步改**。

```
起始帧  QRT1|S|<会话号>|<起始序号>|<总包数>|<分包字节>|<文件字节>|<b64(文件名)>|<crc32>
数据帧  QRT1|D|<会话号>|<序号>|<crc32:8位小写hex>|<b64(分片数据)>
结束帧  QRT1|E|<总包数>|<文件字节>|<sha256>|<b64(文件名)>|<crc32>
```

* **序号**从 0 开始，共「总包数」个；最后一包可能不足「分包字节」。
* **会话号** = `sha256(文件内容)` 的前 16 位十六进制，**三种帧里都带着**。
  同一个文件重复发送时会话号相同，接收端据此认出「这是同一个文件的续传」而不是新文件；
  文件内容一变会话号就变，接收端会问你要不要丢弃旧进度。
* **数据帧也带会话号**，这一条很关键：如果发送端换了文件而接收端的起始帧没扫到，
  新文件的数据帧会因为会话号对不上被直接丢弃并报警。没有这道闸的话，只要新旧文件
  大小相同，新文件的数据就会被按偏移写进旧文件没传完的会话里，而结束帧的总包数、
  文件大小全都对得上、整文件 SHA 也自洽（字节就是新文件本身），最后会**用旧文件名
  存下新文件的内容还报成功**——这是整文件校验也拦不住的静默错误。
* **数据帧的 crc32** 在中间，覆盖「会话号 + 序号 + base64 数据」：
  `crc32(("<会话号>|<序号>|<b64数据>").encode("ascii"))`。
* **起始帧/结束帧的 crc32** 在末尾，覆盖它前面的整串内容。这三种帧都带校验，
  任何一帧被解错都只会被「当作没解出来丢掉」，绝不会让接收端拿着错参数建会话，
  也不会把好数据误判成校验失败。
* **结束帧的 sha256** 是整文件（不是分片）的 SHA-256，用于最后的总校验。

> 接收端还要求同一个二维码被**独立解出 2 次**（可配置）且内容完全一致才认账，
> 这是防误码的第一道闸；上面这些 crc32 / sha256 是第二道。

接收端的三条硬规则：

1. 只接受**正好等于当前缺失序号**的包；
2. 序号**小于**当前缺失序号的，视为重复帧静默丢弃（自动去重）；
3. 序号**大于**当前缺失序号的，判定为缺包，报警并停止接收后续数据。

## 七、临时文件与断点续传

接收端是**边收边写盘**的，不是全憋在内存里：

* `<文件名>.qrtpart` —— 收下来的数据，按 `序号 × 分包字节` 的偏移直接写入；
* `<文件名>.qrtstate` —— 进度（JSON，含一个记录「哪些包已收到」的位图）。

这两个文件每收 8 个包就原子更新一次（先写临时文件再改名，断电也不会写出半个状态文件）。

所以：**接收端被关掉、崩掉、甚至机器重启，进度都在**。重新打开接收端、发送端一发这个
文件的起始帧，接收端会自动认出「这是没传完的那个文件」，接着收，日志里会写：

```
发现未完成的传输，已接着收：报表.xlsx，已收 137/1200 包
```

收齐并通过校验后，`.qrtpart` 会被改名成正式文件，`.qrtstate` 会被删掉，不留垃圾。

> 注意：会话是按**输出目录 + 文件名**找的。如果换了输出目录，旧进度就找不到了
> （旧目录里的临时文件还在，可以手动拷过来或改回去继续）。

## 八、常见问题

**Q：接收端一直显示「扫描中…等待起始帧」**
* 发送端是不是还没点【开始发送】？
* 截屏范围框错地方了？点【框选二维码区域】重新框，让二维码落在框里。
* 二维码太小。发送端窗口最大化或按 F11 全屏，让状态栏里的「像素/模块」不低于 4。

**Q：接收端频繁报缺包（每隔几十包就停一次）**
* 最常见的原因是**框选区域太小**，把数据帧的大二维码边缘裁掉了。用「整个屏幕」重试一次，
  如果好了就是这个原因。参见第二节关于框选的说明。
* 其次看远程桌面客户端有没有开画面缩放；有就关掉，用原生分辨率。
* 再把【分包大小】降到 400~600，【纠错级别】换成 Q。

**Q：接收端日志里一堆「丢弃一个校验码不对的帧」**
* 说明二维码能解出来但内容对不上，通常是远程桌面压缩太狠。把纠错级别调到 Q，
  或者把分包大小降到 400~600（二维码变稀疏，抗压缩能力更强）。

**Q：帧率上不去 / 进度很慢**
* 看接收端右下角「已采样 N 帧（x 帧/秒）」。如果远低于设定的采样帧率，说明截屏或解码
  太慢：把截屏范围框小一点（只框二维码），或者把采样帧率调低（避免无谓的解码开销）。

**Q：发送端状态栏显示「N 像素/模块」是红色警告**
* 二维码太小了，接收端很可能扫不到。最大化窗口或按 F11 全屏，一般要 4 像素/模块以上，
  6~8 更稳。

**Q：两边参数不一样怎么办**
* 分包大小、纠错级别只影响发送端怎么切、怎么画；接收端是从起始帧里读参数的，
  不需要手动对齐。但**续传时不要改分包大小**——改了包边界就变了，接收端会发现参数
  对不上并询问你是否丢弃旧进度（选「是」就得从头传）。

**Q：文件传送完，接收端存的文件名是什么**
* 用发送端的原文件名。如果输出目录里已经有同名文件，会自动加序号变成
  `报表 (1).xlsx`，**绝不覆盖**已有文件。文件名里的路径分隔符和非法字符会被替换掉。

**Q：能不能不回传、纯自动？**
* 不能。外网到内网没有任何通道，接收端无法告诉发送端「这包我没收到」。所有重发都靠人。
  这也是为什么接收端要把「缺第几包」用最大号的字显示出来。

## 九、自测

仓库里的 `selftest.py` 是给开发/验收用的，**两个 Windows 机器上都不需要它**：

```
python selftest.py            # 全部（端到端那部分要图形环境）
python selftest.py --no-gui   # 只跑不依赖界面的部分
```

它覆盖：协议畸形帧、CRC 篡改、状态机全部边界（重复帧 / 缺包停收 / 手动续传 /
接收端重启续传 / 参数冲突 / 缺包时收到结束帧 / 内容被篡改 / 空文件 / 末包不足 /
越过起始帧直接收数据）、二维码编解码往返、抗压缩退化，以及
**真界面 + 真截屏 + 真解码的端到端还原（含模拟丢包后续传）**。

`selftest_gui.py` 更进一步：它**真的开两个进程、两个界面**（一个发送端一个接收端），
接收端对自己屏幕截屏解码，走完整界面流程：

```
python selftest_gui.py          # Windows 上会弹出两个窗口，能亲眼看一遍
```

> Windows 上用这个脚本做验收最直观：窗口会并排出现，你能看到左边二维码不停翻、
> 右边进度条一直走，最后弹出「还原文件逐字节一致」。
